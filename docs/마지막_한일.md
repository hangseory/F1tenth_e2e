## 1. 조향 — 중립 재조정 (실차 검증 완료)

타이로드를 돌려 서보 중립을 **0.3954 → 0.485** 로 옮겼습니다.

```
servo = -0.761 × steer + 0.485,  소프트 리밋 0.12 / 0.85
  전:  좌 +20.73° / 우 -34.16°   (비대칭 → max_steer 는 약한 쪽을 따름)
  후:  좌 +27.48° / 우 -27.48°   (대칭)
  R_min 0.872 m → 0.634 m   (27% 개선)
```

`max_steer` 는 **손으로 적지 않습니다.** `apply_vehicle.py` 가
`(servo_min − offset) / (−gain)` 으로 계산해 내려보냅니다.

> ⚠ 작업 중 두 번 헤맸습니다 — ① 서보 유지 프로세스가 **두 개** 떠서 0.485/0.553
> 으로 싸우고 있었고 ② `steer_limit_check.py` 가 단발 publish 라 서보가 안 움직였습니다
> (VESC 는 명령이 끊기면 마지막 값을 유지, DDS discovery 도 못 따라감).
> 20 Hz 재발행 타이머로 고쳤습니다.

### 3-2. 자기 IP 를 피어에 자동 추가 (`a5d3b87`) — ★ 중요

**증상:** `./race.sh joy` 로 조작이 안 되고, 전압도 "읽지 못했습니다" 가 떴습니다.
서보·VESC 고장처럼 보입니다.

**원인:** CycloneDDS 를 `AllowMulticast=false` 로 쓰므로 discovery 경로가
`Peers` 유니캐스트 목록 **하나뿐**입니다. 그런데 거기 전날 쓰던 공용 WiFi IP
(`192.168.1.9`)가 남아 있었고 젯슨 IP 는 `172.24.91.115` 였습니다.
그 전까지 돌아간 건 **우연히 피어 IP == 자기 IP** 였기 때문입니다.
어긋나자 **같은 젯슨 안의 두 프로세스도 서로를 못 찾았습니다.**

**결정적 단서:** `./bat.sh` 를 단독으로 돌리면 전압이 읽혔습니다 —
`bat.sh` 는 일부러 `dds_env.sh` 를 안 소싱합니다.

**고친 것:**
- `dds_env.sh` 가 젯슨 **실제 IP 를 피어 맨 앞에 항상** 넣습니다 → 네트워크가
  어떻게 바뀌어도 차 자체는 돕니다. `network.peers` 는 이제 "노트북이 젯슨에게
  인사할 주소" 라는 뜻만 남습니다.
- 현재 대역에 상대 피어가 없으면 **기동 시 경고하고 넘길 IP 까지 알려줍니다.**
  조용한 실패를 보이는 실패로 바꿨습니다.
- `RACE_PEERS` 환경변수로 즉석 재지정 (yaml 수정·커밋·pull 불필요).
- `rviz.sh` 가 젯슨 IP 를 인자로 받습니다:
  ```bash
  ./rviz.sh car1 192.168.50.57      # 젯슨 기동 로그의 [dds] 줄에 찍힌 IP
  ./rviz.sh 192.168.50.57           # 이것도 됨
  ```

> **운영 규칙은 그대로입니다 — 와이파이를 바꿨으면 `./race.sh stop` 후 다시 띄울 것.**
> CycloneDDS 는 기동 시점 IP 에 인터페이스를 고정하고 재바인딩하지 못합니다.

## 4. 속도 — 저속 구간 정지-재출발 해소 (실차 검증 완료)

**증상:** 웨이포인트 최저속 구간에서 "거의 정지, 찔끔, 정지, 찔끔".

**측정 (주행 3건 2124 샘플, race η=0.8):**
```
속도가 매끄럽게 내려오다 → 한 샘플에 0.00 으로 절벽처럼 떨어지고
0.3~1.5s 멈춘 뒤 튀어오른다.  절벽 지점은 매번 0.75~1.03㎧ = 3150~4330 erpm
지령 1.3㎧ 아래: 실제<0.3㎧ 비율 3~6%  /  위: 0.3~0.6%
```
센서리스 FOC 가 로터를 놓치는 것입니다.

**원인 둘:**

1. **`min_speed` 가 바닥 역할을 못 했습니다.** `solve_profile` 안쪽에서만 걸리고,
   그 뒤 체인이 더 깎았습니다:
   ```
   speed  = _profile_speed(...)      # min_speed 반영됨
   speed *= _frenet_speed_scale()    # ← 바닥 밑으로 내려간다 (중간 0.79, 최소 0.45)
   speed  = _launch_limit(...)
   v_lock 클램프
   ```
   `gap_follower`·`pure_pursuit`·`stanley` 는 셋 다 맨 마지막에
   `max(speed, min_speed)` 를 하는데 **`map_controller` 만 빠져 있었습니다.**

2. **바닥값 0.4 가 사각지대 안이었습니다.**

**고친 것 (`4315513`):**
- `map_controller._speed_floor()` 를 배율 뒤·출발램프 앞에 추가 (stanley 와 같은 위치).
  **장애물로 줄인 감속은 올리지 않습니다** (`n_obs>0` 이면 통과) — 안 그러면
  막힌 쪽으로 밀어붙입니다.
- `min_speed` 0.4 → **1.4** 로. 절벽(1.03) 위 36% 여유, 그 코너 물리 한계(1.93) 아래.
- `min_speed` 를 **차량별로 내렸습니다** (`tuning.min_speed` → `speed.min_speed`).
  같은 m/s 가 차마다 다른 erpm 이고, 이 값은 프로파일 맨 끝에서 마찰 한계를
  **덮기** 때문에 공용 파일에 두면 다른 차가 미끄러집니다.
  → `race_script.yaml` 의 0.4 는 그대로. **2호차는 자기 값을 재서 넣으세요.**

> ⚠ **근본 원인은 VESC 쪽입니다** (센서리스 전환 erpm / HFI / 위치센서).
> 이 수정은 사각지대를 **피하는** 것입니다. 모터·배터리·기어비가 바뀌면 다시 재세요.

## 7. μ 측정 — 하한만 나옴

`--bag` 으로 모은 `logs/slip_tests/*_friction.csv` 10개(12,974행)로
`ontrack_sysid`(arXiv:2411.17508)를 돌렸습니다.

**발산했습니다:**
```
반복 4: ★ 명목 모델도 발산 — 중단
  전륜 B=40.000 C=1.700 D=1.694 N E=+1.100
  후륜 B= 1.000 C=1.000 D=0.001 N E=-0.847   ← 후륜 접지력 0 = 퇴화 해
```

**왜:** 마찰 사용률 `rho` 의 **중앙값이 0.245 g** 입니다. 차가 한계 근처에
가본 적이 거의 없습니다. 식별은 타이어가 **포화돼야** B·C·E 를 볼 수 있습니다.

**건진 것 (하한):**
```
파일별 mu_hat(래칫): 0.49 0.53 0.53 0.55 0.56 0.58 0.63 0.64 0.64 0.83
rho p99.9 = 0.684 g
```
**μ 는 최소 0.64, 한 번 0.83.** 지금 쓰는 `tire.mu 0.63`(×pac_d = μ_eff 0.72)은
**틀린 값이 아니라 보수적 하한**입니다. 2호차 이식값이지만 과대평가는 아닙니다.

> 실측 μ 를 **확정**하려면 일부러 미끄러뜨려야 합니다 — `./race.sh slip`,
> 지름 10 m 이상 공간 필요. 평소 주행 bag 으로는 구조적으로 하한밖에 안 나옵니다.
